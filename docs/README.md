# 项目文档索引

仓库根的 `docs/` 放产品与架构约定，分三层，各管一件事。改代码前先看对应文档；文档与代码不一致时，以代码为准并顺手更正文档。

## 三层文档

| 目录 | 管什么 | 什么时候改 |
| --- | --- | --- |
| `designs/` 设计文档 | 定了什么、为什么、没选什么、什么情况下重新讨论 | 做决定的时候 |
| `blueprint/` 蓝图 | 现在到底长什么样：格式、规矩、边角情况，以及它们在哪些代码里、由哪些测试守着 | 设计一变就改，先改蓝图、再改代码 |
| `construction/` 施工方案与施工单 | 一次改动怎么做：改哪几份文档、开发流程、怎么验收 | 开工前写；做完留底，不再改 |

另有 `reference/` 放协议参考（对外的接口、协议字段），`reviews/` 放按日期归档的调研与走查记录，以及团队协作的试错案例——这些案例既约束当前团队，也作为未来全能代理的失败案例集（索引见 [`reviews/README.md`](reviews/README.md)）。

## 书写规范

1. **按编号顺序读。** 设计文档从 `designs/00-设计理念.md` 开始，后面的文档依赖前面的；依赖写在开头。
2. **每条决定都能追溯。** 设计文档里的决定给编号（如 G1、P1），蓝图和施工单引用编号；改了主意就标作废，不悄悄覆盖。
3. **每份设计文档都写清范围。** 固定用「做 / 不做（后置）」两段；没选的路也写一句为什么。
4. **原则按固定结构展开。** 含义、为什么、判断准则、不是什么；具体数值预算留给对应主题文档，不堆在原则里。
5. **状态写进索引表。** `designs/README.md` 和 `construction/README.md` 的索引表带状态列，标「已定 / 草稿 / 待写 / 已作废」与日期。
6. **证据落到样本。** 协议格式、日志格式、请求形状这类要人眼看的东西，存成 `samples/` 下的样本文件，验收时直接看，不靠嘴描述。
7. **中文，短句，不贴代码。** 设计文档讲"怎么干、为什么这么干"，代码放蓝图。

## 代码规范

1. **一文件一职责。** 一个 Go 文件只做一个功能或一组紧密相关的功能；判断标准是「读的人一句话能不能说清这个文件干什么」，说不清就拆。
2. **多种功能拆多文件，单一文件过大也拆。** 不要把多种功能堆进一个文件；单个文件长到难导航（经验值几百行）同样拆。拆不拆、怎么拆按当时情况判断，不搞一刀切。
3. **拆文件不跨层。** `app/internal/` 的包边界由 `designs/01-架构.md` 的分层表定死；文件拆分只在包内做，不把不同层的东西合成一个文件。
4. **测试随文件走。** 功能文件配同名 `_test.go`；一个行为一个用例，测试名 `Test<功能><行为>`。
