# 02 · 网关与路由

依据：`00-设计理念.md` 的 G2（多供应商、可替换）、G6（安全与配额兜底）、G7（可观测）；`01-架构.md` 的 D1（Go）、D4（`gqy-server` 承载网关）。调研依据：`../reviews/2026-11-02-magpie-网关精读.md`。

## 范围

**做：**

- 模型解析：`provider/model`、路由组 `group/id`、裸模型名、默认模型。
- 多 provider 多账号：`providers.json`，环境变量 provider 兜底；账号级日 token 配额与账号级失败转移。
- 路由组：order / rotate / usage 三种策略，组内 fallback。
- 失败转移：只在响应开始前；429 / 5xx / 连接错误 / 超时重试，4xx（除 429）不重试；最多 `max_attempts` 次。
- 健康与冷却：每账号并发上限 + 有界队列；冷却时长可配。
- 会话亲和：同一会话固定 provider/账号，内存态，响应头带 `X-GQY-Provider`。
- 可观测：`requests.jsonl` 一行一请求（不落正文），`/api/gateway/status`。
- 端点：`/v1/chat/completions`（流式兼容）、`/v1/models`；Anthropic / Gemini 端点注册后交给 `03-协议翻译.md`。

**不做（后置）：**

- 订阅账号 OAuth、配额窗口持久化、每日自动唤醒。
- 远程 magpie 级联、SSRF 之外的网络策略。
- 通用中间件链（只在网关层预留接口）。
- 图片 / embedding / 视频端点。

## 决定

### R1 · 候选列表：展开到账号，冷却排后

一个请求进入网关后，按顺序得到候选列表：

1. 解析模型：`group/<id>` → 路由组；`<provider>/<model>` → 指定 provider；裸模型名 → 按各 provider 的默认模型匹配。
2. 展开候选：同一 provider 的每个账号（按配置顺序）是一个候选；没有可用账号时，组的下一个成员接上。
3. 排序：冷却中的候选排到最后；组内按策略（R2）排。
4. **切换边界**：只有在还没有向客户端写出任何字节时，才换下一个候选；一旦开始流式输出，错误直接交还客户端。

### R2 · 路由策略：只做三种

| 策略 | 语义 |
| --- | --- |
| `order` | 按配置顺序，失败换下一个 |
| `rotate` | 每次调用轮换到下一个成员 |
| `usage` | 优先选最近用得最少的成员（带半衰期，避免永远落在第一个上） |

不做 smart / pace / weight：那是为订阅配额和多样价格设计的，GQY 单机单用户用不上。

路由组可嵌套：成员可以是 `provider/model`，也可以是另一个组；组内按策略排序，组外由外层策略决定。

### R3 · 并发、冷却与重试

- 每个 provider/账号一个信号量，超出并发上限的请求进有界队列，等待超过 `queue_timeout_ms` 直接返回明确错误，不无限排队。
- 429 / 5xx / 连接错误 / 超时进入冷却，冷却时长 `cooldown_seconds`（上限 600）；冷却中的候选排到最后，全部冷却则该请求失败。
- 4xx（除 429）不重试、不冷却：请求本身有问题，换账号没用。
- 重试上限 `max_attempts`（上限 5），只在响应开始前累计。

### R4 · 会话亲和：内存态

- 同一会话固定在回答过它的 provider/账号上，复用上游 prompt cache。
- 亲和键 = 会话 id；单机单用户，状态只放内存，重启后重新选择。
- 响应头带 `X-GQY-Provider`，前端与调用方能看到实际由谁回答。
- 后续要多实例或持久化，再加 `affinity.json` 落盘，不在本步做。

### R5 · 多账号与配额

- 一个 provider 可以有多个账号（`accounts`）；账号级失败转移优先于 provider 级。
- 账号级日 token 配额是内存态，超限即把该账号视为不可用，直到窗口重置。
- 密钥只写不读：配置里 `api_key` 允许为空，回退环境变量 `GQY_PROVIDER_<ID>_API_KEY`（ID 转大写、非字母数字转 `_`）；对前端只返回 `api_key_set`，不返回明文。

### R6 · 模型解析规则

输入：`model` 字符串、可选会话 id、可选偏好 provider。

1. `group/<id>`：进路由组，按策略选成员。
2. `<provider>/<model>`：直接指定 provider，不跨 provider 转移（除非该 provider 无可用账号且配置了 fallback）。
3. 裸模型名：按各 provider 的 `default_model` 匹配，命中多个时按 providers 配置顺序。
4. 全部未命中：返回明确的模型不存在错误，不猜。

### R7 · 可观测

`$GQY_HOME/gateway/requests.jsonl`，每行一个请求：

```json
{"ts":"…","request_id":"…","session":"…","provider":"deepseek","model":"deepseek-chat","account":"a1","status":"ok|error|cooldown|no_candidate","http_status":200,"duration_ms":123,"attempt":1,"error_code":""}
```

不记录 prompt / 回复正文（G6）。

`GET /api/gateway/status` 返回：各 provider/账号的健康、冷却剩余、调用数、失败数、当前并发；路由组当前指针。

### R8 · 端点与鉴权

- 对外端点：`POST /v1/chat/completions`（非流式 + 兼容流式）、`GET /v1/models`（列出 provider、模型、路由组）。
- 内部端点：`POST /api/chat` 走同一个网关，不旁路。
- 鉴权：设置 `GQY_AUTH_TOKEN` 后，Bearer / cookie 两种方式覆盖 `/api`、`/v1`、`/v1beta`；未设置则只在回环地址监听时放行本机（安全边界在 `11-安全与沙盒.md` 展开）。

## 数据

### providers.json

```json
{
  "providers": [
    {
      "id": "deepseek",
      "display_name": "DeepSeek",
      "base_url": "https://api.deepseek.com/v1",
      "protocol": "openai-chat",
      "default_model": "deepseek-chat",
      "models": ["deepseek-chat", "deepseek-reasoner"],
      "accounts": [
        {"id": "a1", "api_key": "sk-…", "daily_token_limit": 20000000},
        {"id": "a2", "api_key": ""}
      ],
      "max_concurrency": 2
    }
  ]
}
```

- `id` 唯一；`protocol` 目前只认 `openai-chat`，空值等价；Anthropic / Gemini 协议在 `03-协议翻译.md` 后加入。
- 文件不存在时只用环境变量 provider（`GQY_API_BASE` / `GQY_API_KEY` / `GQY_MODEL`）。
- `daily_token_limit` 为空表示不限制。

### routing.json

```json
{
  "default": {"provider": "deepseek", "model": "deepseek-chat"},
  "groups": [
    {
      "id": "daily",
      "name": "日常",
      "strategy": "order",
      "members": ["deepseek/deepseek-chat", "moonshot/kimi-k2"]
    }
  ],
  "max_attempts": 3,
  "cooldown_seconds": 30,
  "queue_timeout_ms": 1500
}
```

- `groups[].id` 唯一；重复注册报错。
- `members` 支持 `provider/model` 或 `group/id`；裸模型名按该 provider 默认模型解析。
- `strategy`：`order`（默认）/ `rotate` / `usage`。
- 上限：`max_attempts` ≤ 5，`cooldown_seconds` ≤ 600。

## 与 magpie 的差异

| 维度 | magpie | GQY |
| --- | --- | --- |
| 定位 | 服务多个 agent 与订阅计划 | 单机单用户，服务内部 agent loop + OpenAI 兼容客户端 |
| 策略 | smart/pace/weight 等一大套 | 只做 order / rotate / usage |
| 会话亲和 | 落盘、多模式、原生 header 优先 | 内存态、按会话 id |
| 路由组限账号 | `Group.Accounts` | 简化：组内成员即候选全集，fallback 不出组 |
| 卡住诊断 | held report + 504 | 有界队列超时直接明确报错 |
| 协议 | Chat / Responses / Messages / Gemini 全量翻译 | 先 Chat，其余在 `03-协议翻译.md` 逐个开 |

## 验收（本设计对应的最小闭环）

1. 裸模型名、`provider/model`、`group/id` 三种解析各有一个用例。
2. 首个账号 429 → 冷却 → 转到第二个账号；流式已开始时不再切换。
3. 路由组 `rotate` 连续三次落在不同成员；`usage` 优先最闲成员。
4. 4xx 不重试；`max_attempts` 用尽后返回 `no_candidate`。
5. 亲和：同一会话连续两次请求，响应头 `X-GQY-Provider` 相同。
6. 请求日志每行字段完整；状态接口反映冷却与并发。
