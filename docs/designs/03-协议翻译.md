# 03 · 协议翻译

依据：`00-设计理念.md` 的 G3（协议翻译一致）、G6（安全与配额兜底）；`01-架构.md` 的 D1（Go）、provider 层职责（编码、解码、错误分类）；`02-网关与路由.md` 的 R3（重试与冷却）、R8（端点）。调研依据：`../reviews/2026-11-02-magpie-网关精读.md`，以及 magpie `docs/subsystems/gateway-routing.md` 中 Chat / Responses / Anthropic Messages / Gemini 翻译、流式与整段等价、错误分类的段落。

## 范围

**做：**

- 统一内部模型：请求（messages、tools、stream、max_tokens、temperature 等）与响应（thinking / text / tool_call / usage / done 事件）。
- 三种对外协议适配：OpenAI Chat Completions、Anthropic Messages、Gemini generateContent。
- 非流式与流式等价；流式边界样本的目录约定与验收标准。
- 错误归一：把上游错误归一成可重试 / 不可重试，喂给 02 的 R3。
- `/v1/models` 输出形状。

**不做（后置）：**

- Responses、embedding、图片 / 视频端点（01 已后置，保持）。
- 供应商专有字段进入核心层：核心层只认统一模型，翻译层之外看不到供应商专有字段（G3）。
- 通用协议中间件框架：只做明确需要的三种，其余后置（G3）。
- 本文不创建 samples 文件：只定「样本放哪、验收看什么」，样本在施工 / 蓝图阶段落到 `docs/designs/samples/03-协议翻译/`。

## 决定

### C1 · 对内只有一种请求模型

所有 provider 适配器与 agent 层只见一种请求形状：

```json
{
  "model": "deepseek/deepseek-chat",
  "messages": [
    {"role": "system", "content": "你是 GQY"},
    {"role": "user", "content": "读一下这个文件", "images": ["data:image/png;base64,…"]},
    {"role": "assistant", "content": "", "tool_calls": [
      {"id": "call_1", "name": "read", "arguments": {"path": "docs/README.md"}}
    ]},
    {"role": "tool", "tool_call_id": "call_1", "name": "read", "content": "文件内容…"}
  ],
  "tools": [
    {"type": "function", "function": {"name": "read", "description": "读取文件", "parameters": {"type": "object"}}}
  ],
  "tool_choice": "auto",
  "stream": true,
  "max_tokens": 4096,
  "temperature": 0.7,
  "top_p": 1.0,
  "stop": ["END"]
}
```

- `messages` 只有四种角色：system / user / assistant / tool；多模态图片挂在 user 消息的 `images`（data URL）。
- `tool_calls[].arguments` 内部是**对象**，不是字符串；编码到 OpenAI 时才序列化成字符串。
- 协议专有字段（`stream_options`、Anthropic thinking 的 `signature`、Gemini 的 `generationConfig` 等）只存在于对应适配器内，不进核心层。

### C2 · 对内只有一种响应事件流

provider 层只产生五种事件：

| 事件 | 载荷 | 说明 |
| --- | --- | --- |
| `thinking` | `delta` | 思考增量，可折叠，不并入正文 |
| `text` | `delta` | 正文增量 |
| `tool_call` | `index`、`id`、`name`、`arguments_delta` | 工具调用；参数分片累积 |
| `usage` | `prompt_tokens`、`completion_tokens` | 流式时独立发一次；非流式可并入 done |
| `done` | `stop_reason` | 终止事件；stop_reason 值域固定 |

`stop_reason` 值域只有六种：`end_turn` / `tool_use` / `max_tokens` / `stop_sequence` / `safety` / `other`。

- 三种协议各自把终止原因映射到这六种，核心层不出现协议原生枚举。
- 与 `05-会话与产物.md` S2 的关系：provider 层的 `tool_call` 投影成会话层的 `tool` 事件，`usage` 并入会话层 `done` 的用量字段；`question` 由 agent 层产生，不在 provider 层。

### C3 · thinking 独立于 text

- 思考块（OpenAI `reasoning_content`、Anthropic `thinking`、Gemini `thought`）解码成 `thinking` 事件，绝不并入 `text`。
- 编码回上游时，Anthropic thinking 的 `signature` 原样透传：GQY 不解读、不落正文日志（G6）。
- 判断准则：流式与整段里 thinking 与 text 的分界一致；分界由 C8 样本守住。

### C4 · OpenAI Chat Completions：原生透传 + 兼容流式

- `providers.json` 的 `protocol` 取值：`openai-chat`（默认，空值等价）、`anthropic-messages`、`gemini`。
- 上游 protocol 为 `openai-chat` 时，`/v1/chat/completions` 做**原生透传**：请求与响应形状不变，专有字段不丢。透传也是 provider 层的翻译（同构翻译），错误分类照做（C9）。
- 上游不是 `openai-chat` 时，内部模型翻译成 Chat 形状再发。
- 兼容流式：
  - 对外 `stream:true` 返回标准 SSE：`data: {…}` 帧，末尾 `data: [DONE]`。
  - 上游非流式时，把整段结果拆成完整事件序列一次发出：role delta → content / reasoning_content → tool_calls → finish_reason → usage。等价性见 C7。
  - `stream_options.include_usage`：usage 放最后一个 chunk。
- 响应形状：`choices[].message`（非流式）/ `choices[].delta`（流式）、`finish_reason`、`usage`。

### C5 · Anthropic Messages：编码与解码

编码（请求）：

- `system` 支持字符串或 blocks：text 块拼接成 system 消息；image 块并入对应 user 消息的 `images`。
- `messages[].content` blocks：`text` / `image` / `tool_use` / `tool_result`。
  - `tool_use` → 内部 `tool_call`（`input` 反序列化为对象）。
  - `tool_result` → 内部 tool 消息，`tool_use_id` 对齐 `tool_call_id`。
- `tools[].input_schema` → 内部 `tools.function.parameters`。
- `max_tokens` 是必填语义：请求缺省时 GQY 填默认值再转发；`stream`、`temperature` 照写。

解码（响应）：

- content blocks：`text` → text；`thinking` → thinking；`tool_use` → tool_call。
- `stop_reason`：`end_turn` / `tool_use` / `max_tokens` / `stop_sequence` 映射到 C2 的值域。

流式事件族：`message_start` → `content_block_start` → `content_block_delta`（`text_delta` / `input_json_delta` / `thinking_delta`）→ `content_block_stop` → `message_delta`（stop_reason、usage）→ `message_stop`。

- `index` 必须连续；`tool_use` 的 `input` 以 `input_json_delta` 分片发出，客户端拼起来必须是合法 JSON。

### C6 · Gemini generateContent

端点：`/v1beta/models/{model}:generateContent`（非流式）与 `:streamGenerateContent`（流式，`alt=sse`）。

编码（请求）：

- `systemInstruction.parts[].text` → system 消息。
- `contents[]`：role `user` / `model` → user / assistant；parts 支持 `text` / `inlineData` / `functionCall` / `functionResponse`。
  - `functionCall` → 内部 `tool_call`。
  - `functionResponse` → 内部 tool 消息（按 `name` 对齐 tool_call）。
- `tools[].functionDeclarations` → 内部 `tools`。
- `generationConfig`：`temperature`、`topP`、`maxOutputTokens`、`stopSequences` → 内部 `temperature`、`top_p`、`max_tokens`、`stop`。

解码（响应）：

- `candidates[0].content.parts`：`text` → text；`thought` → thinking；`functionCall` → tool_call。
- `finishReason`：`STOP` → end_turn；`MAX_TOKENS` → max_tokens；`SAFETY` → safety；其余 → other。
- `usageMetadata`：`promptTokenCount` / `candidatesTokenCount` → usage。

流式：`data: {…}` 帧；每帧带 `candidates[0].content.parts` 增量；末帧带 `finishReason` 与 `usageMetadata`。

### C7 · 非流式与流式等价

- 定义：同一请求，非流式整段 = 流式事件按序拼接。text、thinking、tool_call 参数逐字一致；usage 一致；stop_reason 一致。
- 适配器以「事件流」为唯一真相，两个方向都要能转：
  - 上游流式 → 非流式：收集全部事件，拼成整段 JSON。
  - 上游非流式 → 流式：整段拆成一次完整事件序列（C4 兼容流式）。
- 上游只支持流式、客户端要整段时（如 Gemini 路径）：由 `streamGenerateContent` 聚合后回整段；流在完成事件前断掉返回 502，**不许返回空 200**。

### C8 · 流式边界样本：放哪、验收看什么

- 目录：`docs/designs/samples/03-协议翻译/`，按协议分子目录：`openai-chat/`、`anthropic-messages/`、`gemini/`。
- 每个边界一个样本：请求文件 `*.req.json` + 期望事件序列 `*.events.jsonl`（流式）或整段响应 `*.res.json`（非流式）。
- 必覆盖：三种协议的整段响应；流式完整序列；thinking 与 text 分界；`tool_use` / `functionCall` 参数分片拼接；错误归一样例（429、400 各一）。
- 验收看：字段齐全（id / index / delta 不丢）；分片拼接后是合法 JSON；usage 恰好一次；终止帧存在（`[DONE]` / `message_stop` / finishReason 帧）。

### C9 · 上游错误归一，喂给 R3

每个适配器把上游错误归一成统一结构：

```json
{"code": "rate_limited", "retryable": true, "http_status": 429, "message": "…"}
```

分类规则：

- **可重试**：429、5xx、连接错误、超时、流中途断开（仅对尚未向客户端写字节的请求）。
- **不可重试**：4xx（除 429），含参数错、鉴权错、模型不存在、上下文超长。

- R3 只消费 `retryable` 与冷却信号，不解析供应商错误体；切换边界沿用 R1：只在响应开始前换候选，流式已开始则错误直接交还客户端。
- 对外错误体保持协议形状：
  - OpenAI：`{"error": {"message": "…", "type": "…", "code": "…"}}`
  - Anthropic：`{"type": "error", "error": {"type": "…", "message": "…"}}`
  - Gemini：`{"error": {"code": 400, "message": "…", "status": "…"}}`

### C10 · 错误码与 HTTP 状态码映射

| 场景 | 内部 code | retryable | 对外 HTTP |
| --- | --- | --- | --- |
| 请求体非法、参数错 | `invalid_request` | 否 | 400 |
| 缺鉴权 / 密钥无效 | `auth_required` | 否 | 401 |
| 密钥无权限 | `permission_denied` | 否 | 403 |
| 模型不存在 | `model_not_found` | 否 | 404 |
| 上下文 / 请求体超限 | `context_length_exceeded` | 否 | 400（上游报 413 时保留 413） |
| 限流 / 配额 | `rate_limited` | 是 | 429 |
| 建连 / 读写失败 | `connection_error` | 是 | 502 |
| 上游 5xx | `provider_error` | 是 | 502 |
| 上游超时 | `upstream_timeout` | 是 | 504 |
| 候选耗尽 / 全部冷却 | `no_candidate` | 否（本请求终态） | 503 |
| 流开始后中断 | `stream_interrupted` | —（状态已发 200） | 已发 200，协议允许时补错误帧 |

- 流式已开始：无法改 HTTP 状态。OpenAI 补 `data:{"error":…}` 后断开；Anthropic 发 `error` 事件；Gemini 发 error 块；协议不允许时直接断开，请求日志记 `stream_interrupted`。
- `no_candidate` 是网关重试耗尽后的终态（R3），对外 503 表示「稍后再试」，但不在本请求内再切换候选。

### C11 · `/v1/models` 输出形状

OpenAI 兼容 `object: list`；provider 模型与路由组都列在 `data` 里，路由组以 `group/<id>` 作为 id。

```json
{
  "object": "list",
  "data": [
    {"id": "deepseek/deepseek-chat", "object": "model", "owned_by": "deepseek", "created": 0, "display_name": "DeepSeek Chat", "default": true},
    {"id": "deepseek/deepseek-reasoner", "object": "model", "owned_by": "deepseek", "created": 0},
    {"id": "group/daily", "object": "model", "owned_by": "group", "created": 0, "display_name": "日常", "members": ["deepseek/deepseek-chat", "moonshot/kimi-k2"]}
  ]
}
```

规则：

- `object` 保持 `"model"`，保证 OpenAI 客户端可用；`display_name`、`default`、`members` 是 GQY 扩展，标准客户端忽略。
- `owned_by` 为 provider id 或 `"group"`；`default` 只标记 providers.json 的默认模型；`members` 仅路由组带。
- 列表顺序：providers.json 的 provider 顺序在前，路由组在后。
- 不返回任何密钥字段（G6）。

## 验收

1. 三种协议各有一个「请求 → 内部模型 → 响应」往返用例，字段映射逐一断言。
2. 非流式与流式等价：同一请求两种模式拼出的 text / thinking / tool_call / usage / stop_reason 一致（对照 C8 样本）。
3. 流式边界样本通过：分片拼接合法、usage 恰好一次、终止帧存在。
4. 错误归一：上游 429 / 5xx 判 `retryable`、4xx 判非 `retryable`，并驱动 R3 的转移 / 冷却；R3 不重复解析供应商错误体。
5. `/v1/models` 输出与 C11 形状一致，含 provider 模型与路由组，无密钥字段。
