# 04 · 插件运行时

依据：`00-设计理念.md` 的 G4（插件可扩展）、G5（评测驱动）、G7（可观测）；`01-架构.md` 的 D1（Go）、D3（插件自带运行时）与分层表；`02-网关与路由.md` 的编号习惯。调研依据：magpie 插件运行时文档（<https://raw.githubusercontent.com/yetone/magpie/main/docs/subsystems/plugin-runtime.md> 与 plugin-tools.md），只借鉴机制，不复制。

## 范围

**做：**

- 统一调用模型：业务只认「调用(插件ID, 动作, 参数)」；四层边界与职责。
- 三种适配器：原生 stdio 换行 JSON-RPC、MCP stdio、unix / tcp 远程。
- 生命周期状态机、并发模型、调用超时与取消、进程组回收。
- 热更新：安装 / 卸载 / 重装语义、幂等、provides / requires 依赖检查。
- 插件动作注册成外部工具，随运行时开关注入模型。
- 插件管理接口 `/api/plugins*` 与契约测试清单。

**不做（后置）：**

- 动态加载 Go `.so` / WASM；远程 gRPC、TLS 认证、插件市场。
- 依赖的自动级联加载与拓扑编排：当前只做前置检查，不自动加载依赖。
- 权限系统与沙盒（交给 `11-安全与沙盒.md`）；安装插件 = 信任它。
- 自动重启、熔断、心跳、流式调用、事件订阅。
- 运行时热重配：改 manifest 只走重载，不热改参数。

## 决定

### P1 · 统一调用模型：一个入口，四层各管一件事

业务层只用一种方式调用插件：

调用(插件ID, 动作, 参数) → (内容, 错误)

- 参数与内容都是 JSON；文本工具的内容是字符串。
- 错误是结构化错误，只出这几种：`not_found`、`not_ready`、`timeout`、`invalid_argument`、`call_failed`、`exited`、`canceled`。
- 业务层不关心插件来自哪个社区、是子进程还是远程服务。

四层自上而下，依赖只允许单向：

```
业务层      调用(插件ID, 动作, 参数)
   ↓
运行时层    注册表、生命周期状态机、并发放行、超时、可观测、进程托底
   ↓
注册中心层  选适配器：显式指定 → 社区名匹配 → 探测
   ↓
适配器层    把社区协议翻译成统一模型；社区专有类型只在这里
```

边界只有一条判据：核心层不出现任何社区专有字段；新增一个社区 = 新增一个适配器 + 跑一遍契约测试，核心代码零改动（G4）。

### P2 · 注册中心：三级选择，歧义报错

适配器选择固定三级，逐级尝试：

1. **显式指定**：manifest 的 `protocol` 精确对应适配器名，直接选中。
2. **社区名匹配**：`protocol` 缺省时，按 manifest 的 `community` 字段匹配适配器声明的社区名，且协议版本兼容。
3. **探测**：前两级都没有时，逐个调用适配器的识别（只读、无副作用、失败返回「不匹配」），命中多个即报错。

命中多个适配器时直接报错，要求显式指定，不用注册顺序兜底；否则线上行为不可预期。

### P3 · manifest：字段与约束

插件目录 `$GQY_HOME/plugins/<id>/` 下放 `manifest.json`：

```json
{
  "id": "echo",
  "name": "Echo 示例",
  "version": "1.0.0",
  "description": "回显参数，用于验证插件链路",
  "protocol": "gqy-jsonrpc-v1",
  "command": ["node", "index.js"],
  "cwd": ".",
  "env": {"FOO": "bar"},
  "timeout_ms": 10000,
  "concurrency": "concurrent",
  "actions": [
    {
      "name": "echo",
      "description": "回显 text 参数",
      "schema": {"type": "object", "properties": {"text": {"type": "string"}}, "required": ["text"]}
    }
  ],
  "provides": ["text-echo"],
  "requires": []
}
```

字段约束：

- `id`：`^[a-z0-9][a-z0-9_-]{0,31}$`，全局唯一，重复注册报错。
- `protocol`：`gqy-jsonrpc-v1` / `mcp` / `unix` / `tcp`；可缺省，缺省时走 P2 的后两级。
- `community`：可选，仅 `protocol` 缺省时用于社区名匹配。
- `command`：数组，不经过 shell；相对路径以 manifest 目录为基准；unix / tcp 忽略。
- `cwd`：相对 manifest 目录，默认 manifest 目录。
- `env`：在宿主环境上追加，不覆盖 `PATH` 等关键变量。
- `timeout_ms`：单次调用超时，默认 10000，上限 120000。
- `concurrency`：`concurrent`（默认）/ `single-channel` / `exclusive`。
- `actions`：仅原生协议使用；MCP 走 `tools/list` 发现。
- `address`：unix / tcp 必填，socket 路径或 `host:port`。
- `provides` / `requires`：服务依赖，可选，见 P10。

### P4 · 适配器：三种，社区协议只在适配器里

适配器只实现一个最小契约：识别（读 manifest，判断是否属于本社区）、加载、调用、关闭，并声明并发模型（P6）。社区私有字段一律不进统一模型。

**原生 stdio 换行 JSON-RPC**（`gqy-jsonrpc-v1`）

- 拉起 `command` 进程，标准输入输出上一行一个 JSON-RPC 2.0。
- 方法：`initialize` / `call` / `shutdown`。
- 加载成功 = 进程启动 + `initialize` 成功。
- 调用 `call`，参数 `{action, arguments}`，结果取 `result.content`，错误取 `error.message`。
- `shutdown` 后进程自行退出。

```json
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocol":"gqy-jsonrpc-v1"}}
{"jsonrpc":"2.0","id":1,"result":{"ok":true,"name":"echo","version":"1.0.0"}}
{"jsonrpc":"2.0","id":2,"method":"call","params":{"action":"echo","arguments":{"text":"hi"}}}
{"jsonrpc":"2.0","id":2,"result":{"content":"hi"}}
{"jsonrpc":"2.0","id":3,"method":"shutdown"}
```

**MCP stdio**（`mcp`）

- 拉起 `command` 进程，按 MCP stdio 最小集：`initialize`（protocolVersion `2024-11-05`，capabilities `{}`，clientInfo）→ `notifications/initialized` → `tools/list` → `tools/call`。
- 动作来自 `tools/list` 的 `result.tools[]`（`name` / `description` / `inputSchema`）。
- `tools/call` 返回 `result.content[]`，文本拼接为内容；`isError` 视为错误。
- 关闭走 `shutdown` 再关 stdin。动作名保留原始 `name`，注册成工具时再加前缀（P11）。

**unix / tcp 远程**（`unix` / `tcp`）

- 连接已运行的远程服务，**不拉起进程**。
- 同一套换行 JSON-RPC（`initialize` / `call` / `shutdown`）。
- 加载成功 = 连接建立 + `initialize` 成功。
- 关闭 = 发 `shutdown` 后断开连接，**绝不杀远程进程**。
- 连接断开视为实例 `failed`；业务错误与连接错误分开，连接错误返回 `exited`，不重试。

### P5 · 生命周期状态机

状态：加载中(loading) → 就绪(ready) → 关闭中(closing) → 已关闭(closed)，外加终态失败(failed)。

- 加载中：进程启动 + 协议初始化 + 工具注册（P11）；失败进入失败。
- 就绪：唯一允许调用的状态；其余状态返回 `not_ready`。
- 关闭中：拒绝新调用，等在途结束，再走进程回收（P8）。
- 已关闭：回收完成，从实例表摘除。
- 失败：加载失败回滚后、或运行中进程退出后的终态；可重新加载。

规则：

- **加载失败回滚**：摘除实例、关闭已启动进程、撤销已注册工具、释放信号量，不残留半成品。
- **关闭幂等**：重复卸载返回 `not_found`，不 panic、不重复杀进程。
- **加载幂等**：已就绪直接返回；加载中返回「加载中」。
- **崩溃不无限重启**：进程退出由等待协程捕获，置失败，在途调用返回 `exited`；不自动重启。

### P6 · 并发模型：适配器声明，运行时放行

manifest 的 `concurrency` 声明插件能接受的调用形态，适配器校验并兜底默认，运行时按模型放行：

| 模型 | 语义 |
| --- | --- |
| `concurrent` | 并发调用直接进适配器；适配器靠请求序号多路复用，保证不串包 |
| `single-channel` | 适配器只有一条逻辑通道；运行时并发提交，适配器内部排队，任何时刻至多一个在途调用 |
| `exclusive` | 实例级互斥；运行时串行化所有调用，加载 / 调用 / 卸载不重叠 |

- 原生与 MCP 的 stdio 都靠「请求序号 → 等待通道」多路复用；响应按序号匹配，错序不串包。
- 实例表用读写锁：加载 / 卸载写锁，查表与调用读锁；单插件实例内部一把锁 + 状态机。

### P7 · 调用超时与取消传播

- 每次调用带 deadline，上限取 manifest 的 `timeout_ms`；到点取消上下文，调用方立即拿到 `timeout`。
- 取消沿两条路传播：
  - 对适配器：标记该次调用作废，晚到的结果丢弃。
  - 对进程：原生协议发 `cancel` 通知（可选项）；MCP 只关闭本次等待。
- 不承诺能中断已经在跑的代码；进程级中断属于回收（P8）。
- 超时后进程仍能正确响应后续调用就继续用；被卡死的进程由进程监控置失败，需重新加载。

### P8 · 进程组回收：EOF 自退 → 5s → SIGTERM → 2s → SIGKILL

只针对运行时拉起的 stdio 进程；顺序固定，任何一步都不无限等：

1. 置关闭中，拒绝新调用，等在途结束（带短超时）。
2. 关闭 stdin：插件读到 EOF 应自行退出，这是协议要求的最后防线。
3. 等 5 秒。
4. 未退 → 对整个进程组发 SIGTERM。
5. 再等 2 秒。
6. 仍未退 → 对整个进程组 SIGKILL。
7. 回收：等待协程回收进程、删除临时目录、关闭管道与 socket 文件、从实例表摘除。

- 启动即独立进程组（Unix 用 setpgid），插件自己起的子进程也在组内，可整组杀；只杀主进程会留下孤儿。
- Windows 用 Job Object 或 `taskkill /T /F` 兜底；差异由适配器屏蔽。
- 父进程异常退出时，靠 stdin EOF（第一层）+ 父死子亡信号 / Job Object（第二层）兜底，不残留孤儿。
- stderr 写入 `$GQY_HOME/plugins/<id>.log`，1MB 轮转；请求正文不进日志（G6）。

### P9 · 热更新：安装 / 卸载 / 重装，全部幂等

- **安装**：把插件目录放进 `$GQY_HOME/plugins/<id>/`，重扫后进入已发现；默认不自动加载，显式加载才进入就绪。
- **卸载**：已加载先卸载，再删目录，重扫移除；未加载直接删目录。
- **重装**：同 id 新版本 = 先卸载旧实例 → 换文件 → 重扫 → 可重新加载。
- **幂等**：重复加载返回已就绪；重复卸载返回 `not_found`；重扫不改变运行中实例，只有 manifest 变化（id / version / protocol / 入口 / 依赖）才触发重载。

### P10 · 依赖：provides / requires 前置检查

- 服务表 = 核心内置服务 + 已就绪插件声明的 `provides`。
- **缺依赖拒绝加载**：加载前检查 `requires`，缺任何一个都拒绝，并报出缺的是哪个。
- **有依赖拒绝卸载**：卸载前检查「谁还在依赖我」，有依赖就拒绝，并报出依赖者。
- **循环依赖拒绝加载**：按声明顺序加载；发现环报错并回滚本次加载。
- 不做自动级联加载：依赖要用户或安装流程自己先加载，运行时只检查、不代劳。

### P11 · 工具注册：动作变外部工具，随开关注入

- 加载成功即把动作注册成外部工具（`tool` 层）；卸载时注销。
- 工具名：`<pluginID>__<action>`，动作名里非字母数字转 `_`，最长 64。
- 原生用 manifest `actions` 的 `name / description / schema`；MCP 用 `tools/list` 的 `name / description / inputSchema`。
- 注册冲突（工具名已存在）→ 加载失败回滚（P5）。
- 默认不注入模型：外部工具只在 `GQY_ENABLE_EXTERNAL=1` 或运行时开关开启时才进 agent 的工具列表；HTTP `/api/plugins/{id}/call` 始终可单独调试调用。

### P12 · 可观测

- `GET /api/plugins`：每个插件的状态、协议、并发模型、pid、启动时间、调用次数、失败次数、最近错误。
- 打点：加载、卸载、调用、超时、进程退出码、强杀次数、孤儿兜底触发次数；孤儿兜底触发应恒为 0，非零即告警。
- stderr 日志见 P8；请求正文不进任何日志（G6）。


## 验收（契约测试清单）

1. manifest：重复 id 报错；id 格式非法拒绝；未知 `protocol` 无适配器匹配并报错。
2. 原生：加载 → `initialize` → `call` → `shutdown` → 卸载全链路；结果与错误翻译正确。
3. MCP：`initialize` → `tools/list` 发现动作 → `tools/call` 调用；`isError` 转为 `call_failed`。
4. 远程：unix / tcp 连接已有服务加载成功，全程不拉起进程；断开后实例置失败。
5. 生命周期：加载失败回滚无残留；卸载幂等；关闭中拒绝新调用；崩溃置失败不无限重启。
6. 并发：10 个并发调用不串包，响应按请求序号一一对应；`exclusive` 串行可断言。
7. 超时：插件 sleep 超过 `timeout_ms`，调用返回 `timeout`；卡死进程被回收。
8. 进程回收：stdin EOF 自退；SIGTERM 未退升级 SIGKILL；父进程异常退出后插件限时自退，无孤儿。
9. 依赖：缺依赖拒绝加载；有依赖拒绝卸载；环拒绝加载。
10. 工具注入：开关开启才注入、关闭即移除；命名冲突回滚加载。
11. 热更新：安装 → 扫描 → 加载；重装先卸载旧实例；重扫不重启运行中实例。
