# 00 · 设计理念

## 题眼

> **千队并行，各自封疆。**

两句各管一半，合起来是这个项目守的东西：

- **千队并行**：多任务、多 agent、多团队同时跑是常态，不是选配。并发、隔离、配额、可观测（MT1–MT8）都是为这句话服务的。
- **各自封疆**：每个任务有自己的边界——并发池、每分钟配额、错误域、会话目录、插件模式（安装只读 / 本地可改）。一个队打满不该拖慢另一个队（PL2、MT3）。
- 合起来：**一条规范的路，很多互不越界的队**。网关定契约（协议翻译、路由、配额、日志），插件长能力，会话留痕迹。

副标：**密钥不出门，能力随便长。**——本地优先（G1）+ 插件可扩展（G4）。

## 基本原则

- 本地优先
- 多供应商、可替换
- 协议翻译一致
- 插件可扩展
- 评测驱动
- 安全与配额兜底
- 可观测

下面逐条展开。每条按同一结构写：含义、为什么、判断准则、不是什么。具体的数值预算与实现方式不在本节，留给对应主题的设计文档。

### 一、本地优先

**含义**

- GQY 跑在用户自己的机器上：一个进程、一份配置、一个数据根，不预装运行时。
- 密钥、会话、产物都落在本机，不经过中心服务器中转。

**为什么**

- 密钥交出去是不可逆的风险。模型请求可以直连供应商，没有理由让第三只手里过一遍。
- 常驻程序的服务质量取决于本机可控的部分：启动、路由、插件调用、产物读写。这些环节必须能独立工作，网络只用于真正需要网络的事。

**判断准则**

- 断网时，本地能做的部分照常：会话管理、插件、产物读写不依赖在线服务。
- 网络失败有明确边界：调模型失败可以转移、重试或冷却，但不会拖垮本地功能。
- 谁用谁付：没用到的能力不加载、不占资源。

**不是什么**

- 不是"必须离线"；是"不依赖在线服务才能跑"。

### 二、多供应商、可替换

**含义**

- 上游是多个 provider 的多个账号，不是某一个供应商。
- 模型按 `provider/model`、路由组 `group/id`、裸模型名三级解析；路由组支持 order / rotate / usage。
- 任何一个供应商出问题，请求可以转移到别的供应商或账号。

**为什么**

- 单一供应商意味着把可用性、价格、合规都押在一家身上。
- 供应商的限流、故障、价格变动是常态，网关的价值就是把"选谁"变成配置而不是改代码。

**判断准则**

- 加一个供应商只改配置，不改代码。
- 响应开始前可以失败转移；429 / 5xx / 连接错误可重试，4xx 不重试。
- 路由策略是数据，不是硬编码。

**不是什么**

- 不是"所有供应商都支持"；是"支持哪几家、各家支持什么，由适配器如实声明，不在核心里猜"。

### 三、协议翻译一致

**含义**

- 对内只有一种模型调用模型；OpenAI 兼容、Anthropic Messages、Gemini generateContent 都是这个模型之上的翻译。
- 对外暴露标准端点：OpenAI 兼容 `/v1/chat/completions`、`/v1/models`，以及 Anthropic、Gemini 的协议端点。

**为什么**

- 内部 agent loop 不该为每个供应商写一套代码；外部客户端也只想说一种协议。
- 协议差异（字段、流式事件、错误码）是翻译层的职责，不是业务层的。

**判断准则**

- 流式与非流式等价：同一请求两种模式给出的内容一致。
- 翻译不出错的证据是样本：每种供应商的流式边界、错误、思考块都存成 `samples/` 样本，验收时对照。
- 协议字段不泄漏进核心层；翻译层之外看不到供应商专有字段。

**不是什么**

- 不是"把协议做成通用中间件"；只做明确需要的三种，其余后置。

### 四、插件可扩展

**含义**

- 工具能力分核心工具与插件；插件按社区接入：原生 JSON-RPC、MCP stdio、远程 unix / tcp。
- 业务只认一个统一入口：调用（插件 ID、动作、参数）。

**为什么**

- 内置能力有限，外部能力无限。插件是把"别人的东西"接进来的稳定边界。
- 社区会不断出新协议；架构成立的标准是：新增一个社区 = 新增一个适配器 + 跑契约测试，核心一行不改。

**判断准则**

- 核心层不出现任何社区专有类型；社区字段只存在于适配器内部。
- 插件生命周期（加载中 → 就绪 → 关闭中 → 已关闭）与进程回收由运行时统一托底。
- 安装插件 = 信任它；权限、沙盒是后面 `11-安全与沙盒.md` 的事。

**不是什么**

- 不是插件市场，也不是动态加载任意二进制；先做明确的几种适配器，其余后置。

### 五、评测驱动

**含义**

- 能力不是"看起来能用"，而是用评测证明：三维实验矩阵（prompt / schema / return）、模型裁判、结果落盘可回放。
- 网关、插件、工具的关键路径都有契约测试。

**为什么**

- AI 能力的正确性是概率的，人工点一遍证明不了什么。
- 评测把"改坏了"变成可重复的失败，而不是某天用户发现。

**判断准则**

- 新能力上线前先有评测用例，再谈验收。
- 评测结果落盘，失败可复现、可回放。
- 契约测试覆盖插件的加载、调用、关闭、重复 id、超时、进程退出。

**不是什么**

- 不是追求基准分；是追求"改坏了一测就知道"。

### 六、安全与配额兜底

**含义**

- 访问令牌（Bearer / cookie）覆盖所有对外端点；限流与账号级日配额兜底。
- 密钥只写不读；日志不落正文；请求日志只记元数据。

**为什么**

- 网关暴露的是模型与工具，天然是滥用的目标。
- 配额和限流保护的不只是钱，还有可用性：一个账号被限流，转移到下一个账号。

**判断准则**

- 默认关，需要时开；开了就要可配置。
- 配额、限流、冷却都是内存态与配置，不要求持久化到数据库。
- 正文、密钥、prompt 不进日志。

**不是什么**

- 不是完整的权限系统或计费系统；是"不失控"的兜底。

### 七、可观测

**含义**

- 请求日志（request_id、session、provider、model、状态、耗时、尝试次数、错误码）、健康与冷却状态、插件进程状态都能查到。

**为什么**

- 多供应商、多插件、多协议的组合出错时，没有观测就只能猜。
- 观测是前面六条原则的验收工具：转移有没有发生、配额有没有拦、插件为什么没起来。

**判断准则**

- 每个请求一行 JSONL，字段稳定，可 grep、可统计。
- 状态接口给出当前健康、调用数与冷却，不用翻日志。
- 日志轮转有上限，观测本身不拖垮磁盘。

**不是什么**

- 不是 APM 或全链路追踪；是"出问题能定位"的最小集。

## 写法约定

- 原则的编号是 G1 到 G7；后续设计文档里的决定沿用编号规则（如网关用 R1、插件用 P1），蓝图与施工单引用编号。
- 每条原则的"不是什么"同样重要：它划的是边界，防止原则被无限扩大。
- 具体的数值（超时、上限、冷却秒数）不写在这里，写在对应主题文档，避免两处维护。
