# 01 · 架构

依据：`00-设计理念.md` 的七条原则（G1–G7）。本文只定分层、边界与语言选择；每个部件的细节在对应编号的设计文档里。

## 语言与运行时（先定，其余都依赖它）

### D1 · 后端唯一语言：Go

**决定**：核心、网关、agent loop、插件运行时、评测、HTTP 服务，全部用 Go（当前基线 Go 1.22，标准库优先，少依赖）。

**为什么**

- 单二进制分发，符合 G1「本地优先、不预装运行时」：用户拿到一个可执行文件就能跑。
- 并发模型（goroutine + channel）正好匹配网关与插件运行时的形态：请求转移、并发限制、信号量、进程回收都是天然写法。
- 静态类型 + `go vet` + 表驱动测试，是评测驱动（G5）最便宜的落点。
- 已有代码全部是 Go（`cmd/` 四个子命令、`internal/` 十个包），改语言等于推倒重来，而收益不成立。

**对比过、没选**

| 语言 | 为什么没选 |
| --- | --- |
| Rust | 更省的资源，但生态与团队速度不划算；AI 网关的瓶颈在模型延迟，不在语言 |
| TypeScript/Node 做后端 | 分发要带运行时，违反 G1；长驻进程的并发与进程管理不如 Go 直接 |
| Python | 分发与并发都不合适；只适合离线脚本，不进入服务路径 |

### D2 · 前端：零构建 JS，暂不引入框架

**决定**：前端保持零构建 —— `index.html` + 原生 JS 模块 + CSS，由 Go 进程静态托管。**TypeScript 化是开放问题，待项目主人拍板**。

**为什么暂不引入框架**

- 页面是 AI 工作台：输入框、消息流、灯箱、设置、看板，交互集中在少数几个页面，没有 SPA 的规模需求。
- 零构建意味着改完即刷新，没有构建链；符合 G1「轻量、易用」。
- 现状就是零构建 JS，改动成本最低。

**TypeScript 化的条件**（满足任意一条再提上日程）

- 前端文件数量或协作人数涨到"改一个函数不知道有没有用"的程度；
- 要共享前后端类型（协议、消息结构、工具 schema）；
- 引入组件化 UI，手工 DOM 开始重复。

**到时的迁移路径**：保留零构建，先上 `tsc --noEmit` 做类型检查，再决定是否引入构建；不一步跳进框架。

### D3 · 插件语言 = 插件自带运行时

**决定**：核心不假定插件用什么语言写。原生插件是 stdio 上的换行 JSON-RPC，MCP 插件是 stdio 上的 MCP，远程插件是 unix / tcp 连接。官方示例用 Node（`plugins/echo`、`plugins/mcp-echo`），但 Go、Python 写的插件同样能接。

**为什么**

- 这是 `00-设计理念.md` G4 的直接推论：新增社区 = 新增适配器，核心一行不改。
- 插件进程由运行时托管与回收，语言不是核心的负担。

## 进程形态

### D4 · 一个服务二进制 + 三个工具子命令

| 命令 | 职责 |
| --- | --- |
| `gqy-server` | 常驻服务：HTTP API、网关、agent loop、插件运行时 |
| `gqy-eval` | 评测：三维实验矩阵、裁判、落盘与回放 |
| `gqy-clean` | 维护：按 TTL 清理会话临时产物、日志 |
| `gqy-import` | 维护：导入外部会话/数据 |

评测与维护独立成子命令，不塞进常驻进程：它们是一次性任务，不进热路径，也不该占服务的并发额度（G1「谁用谁付」）。

## 分层总览

依赖只允许自上而下；下层不得 import 上层。每一层对应一个 `internal/` 包或一组包。

```
┌─────────────────────────────────────────────┐
│ 前端  index.html + js/* + styles/*（零构建）   │
└──────────────────┬──────────────────────────┘
                   │ HTTP / SSE
┌──────────────────▼──────────────────────────┐
│ httpapi   路由、鉴权、限流、文件、协议端点       │
└──────┬───────────────┬──────────────────────┘
       │               │
┌──────▼───────┐ ┌─────▼──────────────────────┐
│ gateway      │ │ session  会话、消息、草稿、    │
│ 路由组、转移、│ │ 产物、附件、会话镜像          │
│ 健康/冷却、配额│ └──────────────┬──────────────┘
└──────┬───────┘                │
       │                        │
┌──────▼──────────────────────┐ │
│ agent  agent loop：组装请求、 │◄┘
│ 流式累积、工具调用编排         │
└──────┬──────────────┬────────┘
       │              │
┌──────▼──────┐ ┌─────▼───────────────────────┐
│ provider    │ │ tool  核心工具 + 插件运行时     │
│ 协议翻译     │ │  registry → adapter → 进程     │
│ (openai/    │ └──────────────┬───────────────┘
│  anthropic/ │                │
│  gemini)    │       ┌────────▼────────┐
└──────┬──────┘       │ plugin  生命周期  │
       │              │ 并发模型、进程回收 │
┌──────▼──────────────▼───────────────────────┐
│ 存储  $GQY_HOME：会话落盘、产物、请求日志、     │
│ providers.json / routing.json / 插件目录      │
└─────────────────────────────────────────────┘
```

`eval` 不在这条线上：它复用 `gateway`、`tool`、`plugin` 的能力，但只在 `gqy-eval` 子命令里运行。

## 各层职责与边界

| 层 / 包 | 职责 | 不许做的事 |
| --- | --- | --- |
| 前端 | 渲染、输入、SSE 消费、灯箱、设置、看板 | 不直接碰文件系统；不保存密钥 |
| `httpapi` | 路由、鉴权（`GQY_AUTH_TOKEN`）、限流、上传下载、协议端点注册 | 不写路由策略；不碰供应商协议细节 |
| `gateway` | 模型解析、路由组、失败转移、健康/冷却、并发限制、配额、请求日志 | 不做协议翻译；不做会话管理 |
| `session` | 会话、消息、草稿、产物与附件、会话镜像 | 不直接调模型；不管理插件进程 |
| `agent` | 组装请求、流式累积、工具调用编排、ask_user | 不实现工具；不解析协议 |
| `provider` | 协议翻译：OpenAI 兼容 / Anthropic / Gemini 的编码、解码、错误分类 | 不选路由；不落盘 |
| `tool` | 核心工具（read / edit / shell / websearch / ask_user…）、外部工具注入 | 不托管插件进程 |
| `plugin` | 适配器、生命周期状态机、并发模型、超时、进程组回收 | 不出现社区专有类型（G4） |
| 存储 | 目录规范、会话落盘、请求日志、配置读写 | 不参与运行时决策 |

## 关键数据流

**一次对话请求**：

1. 前端 `POST /api/chat`（或外部客户端 `POST /v1/chat/completions`）→ `httpapi` 鉴权限流。
2. `session` 取出或新建会话，交给 `agent` 组装请求。
3. `agent` 需要模型时走 `gateway`：解析模型 → 选路由组 → 选 provider 与账号 → 调 `provider` 翻译。
4. `provider` 把统一模型调用翻译成供应商协议，流式结果逐块送回 `agent` 累积。
5. `agent` 需要工具时走 `tool`：核心工具直接执行；插件动作交给 `plugin` 运行时。
6. 结果经 `httpapi` 以 SSE 推给前端，`session` 落盘，`gateway` 写一行请求日志。

**一次插件调用**：`tool` → `plugin` 注册中心选适配器 → 适配器翻译成该社区协议 → 运行时按并发模型放行、加超时 → 回收结果。
