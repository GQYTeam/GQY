# 08 · 鉴权与配额

依据：`00-设计理念.md` 的 G6（安全与配额兜底）、G7（可观测）；`01-架构.md` 的 D1（Go）、D4（`gqy-server` 承载 HTTP 服务）；`02-网关与路由.md` 的 R1（候选列表）、R3（并发、冷却与重试）、R5（多账号与配额）、R8（端点与鉴权）；`12-配置与热更新.md` 的 CF8（密钥只写不读）。协议端点的错误形状沿用 `03-协议翻译.md`。

## 范围

**做：**

- 访问令牌 `GQY_AUTH_TOKEN`：Bearer / cookie 两种携带方式，覆盖 `/api`、`/v1`、`/v1beta`；未设置时仅本机可用。
- 全局请求限流：按客户端 IP、固定窗口；与网关账号并发/冷却分层，分工说清。
- 账号级日 token 配额：内存态，超限视为不可用直到窗口重置（呼应 R5）；与 R3 冷却、R1 候选列表的交互。
- 密钥只写不读：前端与状态接口只返回 `api_key_set`（呼应 CF8）。
- 鉴权 / 限流 / 配额的可观测：状态接口暴露什么。

**不做（后置）：**

- 多用户、角色、权限体系：GQY 是单机单用户，令牌只有「对」和「不对」。
- 配额窗口持久化、跨重启恢复：G6 定了配额是内存态，重启清零。
- 订阅账号 OAuth、配额窗口跨设备同步：后置，同 `02-网关与路由.md`。
- 按模型 / 按路由组 / 按会话的细粒度限流：先做全局，够用再拆。
- 多实例共享计数、分布式限流：单进程，不引入外部存储。
- 请求 / 响应正文 masking：日志与工具参数已脱敏，全文 masking 后置。

## 决定

### A1 · 访问令牌：默认关，开启后覆盖全部对外端点

设置 `GQY_AUTH_TOKEN` 后启用鉴权，覆盖 `/api`、`/v1`、`/v1beta` 三组前缀下的全部端点；静态文件与 `/api/auth` 登录端点除外（否则无法登录）。未设置时鉴权关闭，回到「仅本机」模式（A3）。

**为什么**：G6「默认关，需要时开」；网关暴露模型与工具，一旦对局域网开放就必须有一道统一的门。覆盖全部端点而不是只保护写操作，是因为读端点（会话、模型列表、状态）同样泄露信息。

### A2 · 携带方式：Bearer 与 cookie，常量时间比较

两种方式二选一通过即可：

- 请求头 `Authorization: Bearer <token>`（外部客户端与 OpenAI 兼容调用方首选）。
- cookie `gqy_token`（HttpOnly、SameSite=Lax；TLS 或 `X-Forwarded-Proto: https` 时加 Secure），由前端登录后持有。

令牌比较用常量时间比较，不因前缀命中而提前返回。`/api/auth` 接受前端提交的 token，校验通过后种下 cookie，MaxAge 7 天。

**为什么**：两种方式服务两类调用方——程序化调用用 Bearer，浏览器页面用 cookie，避免前端把令牌存进 localStorage。常量时间比较防时序侧信道，这是本地工具对「猜令牌」最便宜的防护。

### A3 · 未设置令牌时只放行本机

未设置 `GQY_AUTH_TOKEN` 时，服务只在回环地址（`127.0.0.1` / `::1`）监听时放行请求。绑定非回环地址且没有令牌，属于需要用户显式确认的安全边界，检测与提示细节在 `11-安全与沙盒.md` 展开。

**为什么**：默认安全（G6）——不设令牌就默认只信本机；把「局域网暴露」变成一个需要用户主动选择并知情的行为，而不是静默发生。

### A4 · 全局限流：每客户端每分钟，固定窗口

`GQY_RATE_LIMIT`（`settings.json` 的 `rate_limit`，0 表示不限）对 `/api`、`/v1`、`/v1beta` 按客户端 IP 做每分钟固定窗口计数；超限返回 429 并带 `Retry-After: 60`。计数键用 `RemoteAddr` 的 IP，不信任 `X-Forwarded-For`（防伪造绕过）。限流在鉴权外层执行：未认证的请求同样计数，防暴力猜令牌。

**为什么**：保护的是 HTTP 服务本身，不是上游供应商——所以放在入口、先于鉴权、只认连接对端 IP。固定窗口 + 内存桶最简单，够单机单用户用。

### A5 · 两层防护分工：入口限流 vs 账号并发 / 冷却

| 层 | 防什么 | 在哪 | 超了怎么办 | 恢复 |
| --- | --- | --- | --- | --- |
| 入口限流（A4） | 打爆本机 HTTP 服务、暴力猜令牌 | `httpapi` 入口 | 429，不进网关 | 下一分钟窗口 |
| 账号并发 / 冷却（R3） | 打爆某个上游账号、供应商限流 | `gateway` 每账号 | 排队或转移候选；全冷却则失败 | 冷却到期 |

两层独立、叠加生效：限流命中不占账号并发与配额，也不产生供应商调用；冷却中的账号照样受入口限流约束。本文只管第一层，第二层规则不变（R3）。

**为什么**：一个是「门」，一个是「供应商侧资源管理」，对象不同、恢复周期不同，不能互相替代，也不能合并成一个参数。

### A6 · 账号级日 token 配额：内存态，超限不可用直到窗口重置

`providers.json` 的 `accounts[].daily_token_limit` 给账号设日 token 上限；为空表示不限。用量按自然日（UTC）窗口在内存里累加，从上游返回的 usage 计 token；达到上限后该账号视为不可用，直到窗口重置。重启清零，不持久化（G6）。

**为什么**：配额兜的是「钱」——一个账号超了换下一个，而不是打爆同一张卡。内存态符合 G6「配额、限流、冷却都是内存态与配置，不要求持久化」。

### A7 · 配额与候选列表、冷却的交互

- 展开候选（R1）时，配额用尽的账号直接剔除，等同「无可用账号」；账号级失败转移优先于 provider 级（R5）。
- 冷却中的账号排到最后（R1），配额用尽的账号根本不进候选——一个是「暂时别用」，一个是「今天别用」。
- 全部账号不可用（冷却或配额）时，该请求返回 `no_candidate`。
- 配额与冷却独立记账：冷却到期自动恢复；配额只等窗口重置。两者叠加时该账号同样不可用。

**为什么**：把「不可用」的两个原因在候选阶段就分清楚，路由决策才可解释；也避免把配额用尽当成冷却去重试。

### A8 · 密钥只写不读

前端与所有读接口（provider 列表、`/api/gateway/status`、配置查看）只返回 `api_key_set`，不返回 `api_key` 明文；日志、限流与配额的错误信息不打印密钥。与 CF8、R5 同一条边界，不因鉴权与配额路径重复定义。

**为什么**：密钥交出去不可逆（G6）。鉴权与配额都会经过 provider 配置，必须显式声明这里同样只写不读。

### A9 · 可观测

`GET /api/gateway/status` 在原有健康 / 冷却字段之外，增加：

```json
{
  "auth_enabled": true,
  "rate_limit": 60,
  "accounts": [
    {
      "provider": "deepseek",
      "id": "a1",
      "token_used_today": 3100000,
      "token_limit": 20000000,
      "quota_exhausted": false,
      "cooldown_remaining_s": 0
    }
  ]
}
```

请求日志（R7）在一行里记 `status` 时区分 `rate_limited` 与 `no_candidate`；不记 token 值、不记正文（G6 / G7）。

**为什么**：G7「出问题能定位」——限流有没有拦住、哪个账号配额快用完、为什么请求被拒，状态接口一眼能看，不用翻日志猜。

## 验收（本设计对应的最小闭环）

1. 设置 `GQY_AUTH_TOKEN` 后，无令牌访问 `/v1/chat/completions` 返回 401；带 Bearer 通过；cookie 登录后 `/api/chat` 直通。
2. `/api/auth` 是唯一无需令牌的 `/api` 端点；令牌错误不种 cookie。
3. 未设置令牌且监听 `127.0.0.1`：本机请求放行。
4. `rate_limit=5` 时第 6 个请求返回 429 且带 `Retry-After`；未认证请求同样被计数。
5. 账号 token 配额用尽后，该账号不再进入候选，请求转移到下一个账号；全部用尽返回 `no_candidate`。
6. provider 列表与状态接口只出现 `api_key_set`，看不到明文。
7. 状态接口反映 `auth_enabled`、`rate_limit`、每账号 `token_used_today` / `token_limit` / `quota_exhausted`。
