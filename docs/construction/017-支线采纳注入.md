# 017 · 支线采纳注入

日期：2026-11-02
状态：完成

## 目标

补完 GL4 的合并语义：支线执行完登记为可采纳对象；主线**显式采纳**后，摘要在下一次轮边界注入主线上下文，且**每条只注入一次**。在此之前，支线只能被记录（013/016），采纳只写 Branch 标记，从不影响主线。

## 范围

**做：**

- `goal.Manager.RegisterBranch(goalID, message, output) string`：支线执行完登记，返回 `branch_id`；摘要默认 `原消息 → 输出`。
- `goal.Manager.TakeAdoptions(goalID) []string`：取走「已采纳且未注入」的摘要并标记已注入（一次性）。
- `Branch` 增加 `Injected` 字段；`Adopt` 传空摘要时保留登记摘要（不覆盖）。
- `session.Event` 增加 `branch_id`（SSE/事件流可定位到支线，前端可挂「采纳」）。
- `agent.Loop` 轮边界先注入采纳摘要（user 消息，前缀 `[支线已采纳，纳入主线考虑] `），再执行排队支线。
- `httpapi.agentSink`：`RecordBranch` 登记并带 `branch_id` 写事件；`TakeAdoptions` 委托 goal。
- 测试：登记→采纳→注入一次；未采纳不注入；重复取走为空；不存在的 branch 采纳报错；loop 注入后主线 `messages` 只多一条且只出现一次。

**不做（后置）：**

- 前端「采纳」按钮（SSE 已带 branch_id，按钮后置）。
- 分叉会话落盘与合并（session manifest）。
- 采纳内容的去重/冲突合并策略（当前直接追加）。

## 关键决定

- **采纳是显式动作**：主线不会自动合并支线；只有 `POST /api/goal/{id}/adopt` 才产生注入。
- **只注入一次**：`Injected` 标记保证同一摘要不会每轮重复塞进上下文。
- **降低上下文污染**：注入为单条 user 消息，前缀说明来源；不重放支线全文，只给摘要。
- **空摘要不覆盖**：采纳接口的 `summary` 为空时沿用登记摘要，避免误清空。

5. loop 轮边界把采纳摘要注入主线 `messages`，且整轮只出现一次。
6. `branch` 事件带 `branch_id`。
