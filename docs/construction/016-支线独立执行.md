# 016 · 支线独立执行

日期：2026-11-02
状态：完成（2026-11-02）

## 目标

把 013 的支线「记录」升级为**真实执行**：主线运行中入队的支线消息，在轮边界由 agent loop 各跑一次独立的单轮模型调用，结果写回 `branch` 事件（原消息 + 支线回答），不进入主线上下文；主线继续推进，只有显式采纳才合并。

## 范围

**做：**

- `agent.Branches` 接口改为「取队 + 回收结果」：`TakeQueued() []string` + `RecordBranch(message, output string) error`。
- `agent.Loop` 在轮边界对每条排队消息执行一次独立模型调用（单轮、不带工具、不改主线上下文），失败记为 `支线执行失败: …` 继续主线。
- `branch` 事件扩展为 `{type:"branch", content:原消息, output:支线回答}`。
- `httpapi` 的 `agentSink` 实现新接口：取队 + 写 branch 事件。
- 测试：支线确实执行（streamer 调用次数增加）、结果写回、主线轮数与响应不受影响、支线失败不拖垮主线、FIFO 顺序。

**不做（后置）：**

- 支线多轮/带工具执行（本单单轮、无工具，避免支线产生副作用）。
- 显式采纳合并到主线上下文的自动注入（仍走 `/api/goal/{id}/adopt`，只记摘要）。
- 分叉会话落盘（session manifest 的父会话/合并关系）。

## 关键决定

- **支线单轮、无工具**：支线可能有副作用（工具调用），默认不给工具；需要工具的支线走分叉会话（后续）。
- **主线上下文零污染**：支线请求独立构造（只有一条 user 消息），结果只写 branch 事件。
- **失败不拖垮主线**：支线调用失败只记录，不返回错误给主线。
- **FIFO**：按入队顺序执行；执行完即出队，不重复。

行为验收：

1. 排队 2 条支线，轮边界各执行一次模型调用，按 FIFO 写 2 个 branch 事件（content=原消息，output=支线回答）。
2. 主线响应、主线轮数、主线上下文不受支线影响。
3. 支线模型调用失败时记 `支线执行失败: …`，主线继续。
4. 队列取空后下一轮不再执行。
5. 不带工具：支线请求的 `tools` 为空（模型不会拿到工具声明）。

## 留底

完成（2026-11-02）。

落点：

- `internal/agent/loop.go`：`Branches` 接口改为 `TakeQueued() []string` + `RecordBranch(message, output string) error`；新增 `drainBranches`（轮边界执行，FIFO）与 `runBranch`（单轮、不带工具、独立请求）。
- `internal/httpapi/chat.go`：`agentSink` 实现新接口——`TakeQueued` 从 goal 取队，`RecordBranch` 把结果写成 `branch` 事件（`content`=原消息，`output`=支线回答）。
- 测试 3 个：支线执行与 FIFO（2 条支线 → 2 个 branch 事件、支线请求 tools 为空、主线响应/上下文不受影响、模型调用 4 次）、支线失败记 `支线执行失败: …` 主线继续、空队列零额外调用。全仓 14 个包全绿。

实测观察：`DrainBranches` 在**每轮开始**都执行，包括第一轮——正常路径下第一轮队列为空（HTTP 层只在 loop 运行时入队），不产生额外调用；若进程重启后 goal 里留有旧排队消息，会在下一次 loop 的第一轮被处理。

偏差：

- 支线为单轮、无工具（避免副作用）；需要工具的支线走分叉会话，后置。
- 显式采纳仍只记摘要（`Manager.Adopt`），不自动注入主线上下文。
- 分叉会话落盘（session manifest 的父子/合并关系）仍后置。
