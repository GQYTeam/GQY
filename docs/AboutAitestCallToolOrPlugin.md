# 工具/插件调用评测网关 设计文档

> 目标：用一个网关脚本统一承接"模型请求 + 工具注入 + 工具执行 + 结果记录"，把**提示词、工具说明、工具返回值**三个维度做成可枚举、可组合、可复现的实验变量，跑出评测矩阵，结论落到 `docs/test_call_{tool}/`，用来回答"这套工具到底怎么给模型描述、怎么回传结果，效果最好"。
> 如果你有更好的方法，可以先改此文档：比如那个更能减少提示词来让模型知道怎么使用工具的方式来降低注意力被干扰的概率    
---

## 一、先划清边界

这个网关**不是**业务网关，不承担鉴权、限流、路由那些生产职责。它是一个**评测专用代理**，职责只有四件：

1. **接请求**：从评测用例出发，构造发给模型的请求。
2. **注入工具**：按当前实验组合，把工具说明（schema）、提示词里的工具使用指引、工具返回值渲染策略，三者拼进请求。
3. **执行工具**：模型返回工具调用时，网关真实执行插件（走上一份文档里的适配器/运行时），拿到原始返回值，再按当前渲染策略回填给模型，继续对话直到收敛。
4. **记录一切**：每次交互的请求、响应、工具调用、返回值、最终答案、耗时、token 全部落盘，供离线分析和回归。

**不做的事**：不做模型路由、不做成本优化、不缓存跨用例的响应（同一配置的重复跑要真跑，除非显式开启"重放模式"）。

---

## 二、三个可调维度，先定义清楚

评测的核心是"变量"。三个维度各自的取值集合必须**显式枚举**，不能边跑边改。

### 维度 A：提示词（Prompt）

指系统提示词 + 用户提示词里**与工具使用相关**的部分。典型变体：

| 变体代号 | 内容取向 |
|---|---|
| `prompt-none` | 完全不提工具，纯靠工具 schema 自然触发 |
| `prompt-basic` | 一句话："可用工具如下，需要时调用" |
| `prompt-when` | 明确"什么时候该调、什么时候不该调" |
| `prompt-when-how` | 在 `prompt-when` 基础上加"怎么调、参数怎么填" |
| `prompt-fewshot` | 加 1~3 个正例/反例 |
| `prompt-strict` | 强约束："不确定就不要调""必须先调再答" |

### 维度 B：工具说明（Tool Schema / Description）

指工具的 name、description、参数 schema 及其字段描述。典型变体：

| 变体代号 | 内容取向 |
|---|---|
| `schema-min` | 只有 name + 必填参数，description 一句话 |
| `schema-full` | 完整参数描述、类型、示例、边界说明 |
| `schema-example` | 在 full 基础上给每个参数一个调用示例 |
| `schema-negative` | 显式写"不要用它做什么" |
| `schema-alias` | 同义工具名收敛/拆分（验证命名影响） |

### 维度 C：工具返回值（Return Rendering）

指工具执行完，把结果回填给模型时的形态。典型变体：

| 变体代号 | 内容取向 |
|---|---|
| `ret-raw` | 原始 JSON 原样回填 |
| `ret-trim` | 去掉冗余字段，只留关键字段 |
| `ret-summary` | 自然语言摘要 + 关键字段 |
| `ret-typed` | 结构化 + 显式类型标注（数字/时间/枚举） |
| `ret-error-rich` | 错误时给结构化错误码 + 修复建议 |
| `ret-error-min` | 错误时只给"失败" |

这三个维度的取值集合写在**一份实验配置文件**里，网关只读配置，不读代码。

## 三、实验矩阵与实验设计

### 1. 矩阵规模控制

三维全组合是 A×B×C，很容易爆炸。必须分阶段：

- **阶段一：单因素扫描（控制变量）**。固定两个维度为"默认值"，扫描第三个维度。目的：找出每个维度里哪些变体值得留。
- **阶段二：两两组合**。把阶段一里表现最好的前 2~3 个变体两两组合，验证是否有交互效应（比如 `prompt-when-how` 是否让 `schema-min` 也够用）。
- **阶段三：全组合小样本**。对阶段二胜出的组合做全组合，每个组合跑 N 次（N≥5）看稳定性。
- **阶段四：回归**。把最终胜出配置固化为默认，纳入 CI，任何一方改动都要重跑。

**每一轮只改一个维度的组合必须能被识别出来**——配置里给每个实验打 `round` 和 `axis` 标签，方便汇总时按轮次分组。

### 2. 用例集设计

用例不是随便写，要覆盖工具的"调用决策空间"：

| 用例类型 | 目的 | 示例 |
|---|---|---|
| 必调用 | 该调必须调 | 问需要工具才能答的问题 |
| 不该调用 | 不该调别乱调 | 常识问题、闲聊 |
| 参数歧义 | 参数该填什么 | 缺省值、多候选、单位歧义 |
| 边界值 | 参数边界 | 空、超长、非法枚举 |
| 工具返回异常 | 返回值理解 | 空结果、部分失败、错误码 |
| 多工具选择 | 选对工具 | 两个相似工具选一个 |
| 多轮依赖 | 串行调用 | 第一次返回值决定第二次参数 |

每个用例是"输入 + 期望行为"，期望行为包含：是否调用、调用哪个工具、参数应满足什么约束、最终答案应包含什么关键事实。**不要用"答案完全相等"做判定**，用约束 + 关键事实命中。

## 四、网关脚本怎么组织

用 Go 写，和插件后端同仓。目录建议：

```
cmd/eval-gateway/            # 入口，读配置、跑矩阵、写结果
internal/eval/
├── config/                  # 实验配置解析（yaml）
├── matrix/                  # 组合生成、去重、轮次标签
├── case/                    # 用例加载与校验
├── gateway/                 # 核心：构造请求、注入、调用、回填
│   ├── prompt.go            # 维度A渲染
│   ├── schema.go            # 维度B渲染
│   ├── render.go            # 维度C渲染
│   └── runner.go            # 单次对话循环（含工具执行）
├── judge/                   # 判定器：规则 + 可选模型裁判
├── recorder/                # 落盘：jsonl + 报告
└── replay/                  # 录像重放
```

### 单次对话循环（这是网关的心跳）

一次"用例 × 配置 × 重复次数"的执行，固定流程：

1. 按配置渲染系统提示词、用户消息、工具 schema 列表。
2. 发模型请求，记录完整请求体与响应体（含 token 用量）。
3. 若响应含工具调用：
   - 校验工具名与参数是否合法（先做本地 schema 校验，失败也要记录，但**不拦截**，让模型看到真实结果，除非配置开了"严格校验"）。
   - 调插件运行时执行，拿到原始返回值。
   - 按维度 C 的渲染策略回填为工具消息。
   - 回到第 2 步，最多 N 轮（防死循环）。
4. 若响应是最终答案：结束，进入判定。
5. 若超过轮次上限或超时：标记为"未收敛"，同样进入判定（当作失败样本，但要单独归类）。

**关键约束**：对话循环里任何一步的请求/响应/工具调用/返回值都要进录制，保证可重放。

### 工具执行的接入点

网关不直连插件，只依赖运行时的一个统一调用入口（`调用(插件ID, 动作, 参数)`）。这样评测矩阵可以跨适配器、跨社区复用。评测时把适配器指向"评测宿主环境"：固定数据目录、假密钥、可注入的失败（故障注入开关，用来造 `ret-error-*` 的样本）。

## 五、判定与指标

### 指标（每个配置 × 每个用例聚合）

| 指标 | 含义 |
|---|---|
| 调用决策准确率 | 该调是否调了、不该调是否没调 |
| 工具选择准确率 | 多工具场景选对没有 |
| 参数合规率 | schema 校验通过率 + 关键参数命中率 |
| 返回值利用率 | 依据返回值得出的后续推理是否正确 |
| 端到端成功率 | 用例约束全部满足 |
| 平均轮次 / token / 延迟 | 成本视角 |
| 稳定性 | 同配置 N 次结果一致率 |

### 判定器

- **规则判定优先**：是否调用、调了哪个、参数约束、答案关键事实包含，全部可编程判定。规则判定便宜、可解释、可回归。
- **模型裁判作为补充**：只用于"答案质量"这类主观项，且裁判模型固定、温度 0、判定模板固定。**裁判结果永远标注来源**，不与规则判定混为一谈。
- **人工抽检**：每个配置随机抽 5% 双人复核，校准判定器。

## 六、结果落盘：`docs/test_call_{tool}/`

按工具（或插件）分目录，工具内按"轮次/时间戳"分子目录，保证可追溯、可对比、不覆盖。

```
docs/test_call_{tool}/
├── README.md                    # 本工具的评测结论摘要（人读，最新一次胜出配置写这里）
├── configs/
│   └── {round}-{ts}.yaml        # 该轮实验配置快照（含三维度取值、用例集版本、模型版本）
├── runs/
│   └── {round}-{ts}/
│       ├── runs.jsonl           # 每次执行一行：用例、配置标签、请求、响应、工具调用、返回值、判定、耗时、token
│       ├── trace/{run_id}.json  # 完整对话轨迹（多轮、工具消息全量）
│       ├── cases/               # 本次用到的用例快照（防止用例漂移）
│       └── errors.log           # 网关/插件异常，单独记
├── report/
│   └── {round}-{ts}.md          # 汇总报告：矩阵表 + 各维度对比 + 结论 + 反例清单
└── best/
    └── current.yaml             # 当前胜出配置（被 CI 与线上默认引用）
```

### 落盘字段约定（`runs.jsonl` 每行必须有）

- `run_id`、`case_id`、`repeat_idx`
- `config`: `{prompt, schema, return, model, model_ver, gateway_ver}`
- `round`、`axis`（用于汇总分组）
- `messages`: 请求体（脱敏后）
- `tool_calls`: `[{name, args_raw, args_parsed, schema_valid, exec_ok, ret_raw, ret_rendered, latency_ms}]`
- `final_answer`、`rounds_used`、`tokens{in,out}`、`total_ms`
- `judge`: `{rule: {pass, reasons[]}, model: {pass, reasons[]}, human: optional}`
- `status`: `ok / not_converged / timeout / gateway_error`

### 报告（`report.md`）必须有

1. 实验配置快照摘要（三维度、模型、用例数、重复数）。
2. **矩阵汇总表**：行=配置组合，列=各指标，按端到端成功率排序。
3. **单因素对比图/表**：每个维度内变体的对比，标出显著差异。
4. **交互效应说明**：两两组合是否出现非加性变化。
5. **反例清单**：失败最多的 10 个用例 + 原始轨迹链接。
6. **结论与建议**：胜出配置、为什么、适用边界。
7. **成本**：总 token、总耗时、单次平均成本。

### 版本与可复现

- 每份结果必须记录：模型名与版本、网关版本、用例集版本、插件版本、适配器版本、插件协议版本。
- 配置、用例、代码任一变化，视为新一轮，不能混在同一 `runs.jsonl` 里比较。
- 提供**重放模式**：从 `trace` 回放，不发真实模型请求（用录制的响应），用于快速验证判定器或渲染逻辑改动。

## 七、并发、限流与成本

- 矩阵执行**按配置分组并行**，组内串行（保证同配置的多次重复受同等外部条件影响）。并发度可配，默认小并发。
- 对模型提供方做**令牌桶限流 + 指数退避重试**；重试也要落盘（标记 `retry_of`），不能悄悄吞掉。
- 插件执行设超时与总轮次上限，超时视为失败样本，不重试（重试会污染稳定性指标）。
- 成本控制：阶段一/二用小样本快速筛，阶段三才放大；支持"只跑变化维度"的增量模式。
- **禁止**在评测里开随机温度做主结论；温度固定（通常 0 或很低），稳定性靠重复次数而不是靠高温采样。

---

## 八、和插件系统的结合点

- 网关只依赖运行时的统一调用入口，不依赖具体适配器，因此评测结论对"所有社区"通用；但报告里要标注本次用的是哪个适配器的哪个插件版本。
- 插件加载失败、协议版本不匹配、超时等**运行时错误**，在网关里统一归类为 `gateway_error` 或 `exec_error`，与"模型调用决策错误"分开统计。**混在一起统计会得出错误结论**。
- 故障注入由评测宿主环境提供：能按用例指定"这次插件返回空/返回错误码/超时/慢响应"，用来稳定地产出维度 C 的错误样本。
- 适配器的能力声明（是否支持流式、是否支持事件）会影响网关的构造方式，网关要读能力声明决定走同步还是流式分支。

---

## 九、防污染与防漂移

这是评测最容易翻车的地方，必须写进规范：

1. **用例集冻结**：每轮评测用例集打版本号，跑的过程中不许改。新增用例进下一轮。
2. **判定器冻结**：判定规则一旦用于一轮评测，本轮内不许改。改判定器 = 新开一轮。
3. **配置即事实**：报告里的结论只能引用 `configs/` 里的快照，不能引用"当时我记得改过"。
4. **脱敏**：请求/响应落盘前对密钥、个人数据脱敏，规则固定、可审计。
5. **禁止跨轮比较**：模型版本、用例版本、判定器版本任一变化，历史数据只能做"趋势参考"，不能做"胜出判定"。
6. **`best/current.yaml` 只能由一轮完整评测的胜出结果写入**，手改必须留 commit 说明理由。

## 十、落地顺序

1. 定实验配置格式（三维度枚举 + 用例引用 + 模型参数 + 重复次数），先手工写 1 个工具、3 个用例、每维度 2 个变体，跑通"请求 → 工具执行 → 回填 → 判定 → 落盘"全链路。
2. 补 `runs.jsonl` 与 `trace` 落盘、报告生成，先用 1 个用例验证报告可读。
3. 加矩阵生成与单因素扫描，跑第一轮，验证"改一个维度指标确实变化"。
4. 加两两组合、稳定性重复、增量模式、重放模式。
5. 把胜出配置写入 `best/current.yaml`，接 CI：任何插件/适配器/提示词变更触发回归，回归不达阈值阻断合并。
6. 扩展到第二个工具，验证目录结构与报告模板可复用。

---

## 十一、一句话总结

- **网关**只做四件事：构造请求、注入三维度、执行工具、全量录制。
- **三维度**各自枚举变体，实验分四阶段：单因素 → 两两组合 → 全组合小样本 → 回归固化。
- **判定**规则优先、模型裁判补充、人工抽检校准；运行时错误与模型错误分开统计。
- **落盘**到 `docs/test_call_{tool}/`：配置快照、逐次 runs、完整轨迹、汇总报告、当前胜出配置，全部带版本、可重放、可对比。
- **防翻车**：用例冻结、判定器冻结、配置即事实、禁止跨轮比较、`best/current.yaml` 只由完整评测写入。
