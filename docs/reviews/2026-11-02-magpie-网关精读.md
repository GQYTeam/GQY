# 2026-11-02 · magpie 网关精读

对象：[yetone/magpie](https://github.com/yetone/magpie)（MIT），本次精读重点是其网关路由与失败转移机制，源码锚点 `internal/gateway/gateway.go`，文档锚点 [`docs/subsystems/gateway-routing.md`](https://github.com/yetone/magpie/blob/main/docs/subsystems/gateway-routing.md)。

只记录对 GQY 网关设计有参考价值的结论，不复制其实现。

## 精读结论（对我有用的八条）

1. **候选列表与"响应开始前"切换**。先解析模型（`provider/model`、路由组、别名），再 `plan` 展开候选：同一 provider 的每个账号/key → fallback 模型；处于冷却的排最后。**只有还没有向客户端写出任何字节时**才切换候选；一旦开始流式输出，错误直接交还客户端。这是网关失败转移的硬边界。
2. **路由策略收敛到三种。** magpie 提供 smart / order / rotate / usage / pace / weight / free / fast 一堆策略，但 GQY 是单机单用户、不做订阅配额，只需要 **order / rotate / usage** 三种 + fallback。
3. **健康、冷却、并发分开管。** 每个账号/key 有最大并发，超出进有界队列；429 且仍有额度时进入"休息"、排到所有未限流候选之后，可手动解除；连接错误、超时、5xx 可重试；4xx（除 429）不重试。插件或上游卡住必须有超时，不能拖垮网关。
4. **会话亲和的目的是缓存命中。** 同一会话固定在回答过它的账号上，避免上游 prompt cache 失效；会话身份优先取客户端原生 header（如 `X-Conversation-ID`），其次才是首条消息摘要。GQY 当前单机单用户，先做"同会话固定 provider、内存态、响应头带 `X-GQY-Provider`"。
5. **路由组可以限账号。** magpie 支持把路由组限制在 provider 的某些账号上（`Group.Accounts`），fallback 只在组内允许的账号里进行，不会逃到组外。GQY 的多账号配额应沿用这个直觉：**组是边界，fallback 不出组**。
6. **可观测分三层。** 路由决策（候选、冷却、谁最终回答）、用量（provider/model/token/耗时/状态）、会话聚合（同一会话的请求归并）。GQY 先落 `requests.jsonl` 一行一请求 + `/api/gateway/status`。
7. **路由前被"卡住"的请求要有交代。** magpie 对还没开始路由就被挡住（掩码、排队、上游没回）的请求先展示"routing"，超时给 504 并落诊断报告。GQY 可以简化：有界队列超时直接返回明确错误码，不搞诊断报告。
8. **端点收敛。** 同时服务 Chat Completions、Responses、Anthropic Messages、Gemini 四套协议 + `/v1/models`。GQY 先做 `/v1/chat/completions` + `/v1/models`，Anthropic/Gemini 翻译放 `03-协议翻译.md`。

## 采用 / 不采用

| 能力 | GQY 采用 | 说明 |
| --- | --- | --- |
| 候选列表 + 响应开始前切换 | 是 | 这是失败转移的骨架 |
| order / rotate / usage 三种策略 | 是 | 不做 smart/pace/weight |
| 账号级并发 + 有界队列 | 是 | `queue_timeout_ms` 超时明确报错 |
| 429/5xx/连接错误冷却、4xx 不重试 | 是 | 上限参数化 |
| 会话亲和（内存态） | 是 | 响应头 `X-GQY-Provider` |
| 路由组限账号、fallback 不出组 | 是 | 简化版：组内成员即候选全集 |
| 请求日志 + 状态接口 | 是 | `requests.jsonl`、`/api/gateway/status` |
| 路由前卡住的诊断报告 | 否 | 只做超时报错，不做 held report |
| 订阅账号 OAuth / 配额窗口持久化 | 否 | 后置 |
| 远程 magpie 级联 | 否 | 后置 |
| 通用中间件链 | 否 | 只在网关层留接口 |
