# 2026-11-02 · 配置热更新调研

对象：成熟网关与生产服务的配置热更新机制，以及 Go 文件监视生态。只记录对 GQY「配置与热更新」设计有参考价值的结论，不复制实现。上游依据：`../designs/00-设计理念.md`（G1 本地优先、G6 安全与配额兜底、G7 可观测）、`../designs/02-网关与路由.md`（R1–R8，providers.json / routing.json）。

## 各家怎么做

### Envoy：xDS 动态下发 + hot restart 兜底

- 运行时配置大部分走 xDS 动态下发：路由（RDS）被「优雅替换，不影响现有请求」；监听器（LDS）、集群（CDS）、端点（EDS）、密钥（SDS）各管一段。来源：[Envoy xDS overview](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/operations/dynamic_configuration)。
- 静态配置改动走 hot restart：新进程把配置、服务发现、健康检查全部初始化完成后，才接管监听 socket；旧进程进入 drain，把已有连接服务完或按超时终止；连接不迁移到新进程。来源：[Envoy hot restart](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/operations/hot_restart)。

### HAProxy：`-sf` 平滑重载

- `haproxy -f cfg -sf <旧 pid>`：新进程解析配置，启动后向旧进程发 SIGUSR1，旧进程只解绑端口、继续服务既有连接直到关闭；`-st` 是硬停。master-worker 模式下 master 收到 SIGUSR2 会以 `-sf` 重新执行自己。来源：[HAProxy 2.6 Management Guide](https://docs.haproxy.org/2.6/management.html)、[HAProxy Enterprise 启停文档](https://www.haproxy.com/documentation/hapee/1-5r2/administration/start-stop-haproxy/)。

### Nginx：HUP + worker 交接

- master 收到 HUP 后先查语法，再尝试应用新配置（开日志、开监听）；失败就回滚、继续用旧配置；成功才起新 worker，旧 worker 服务完老客户端后退出。新连接走新 worker，老连接留在旧 worker。来源：[nginx: Controlling nginx — Changing Configuration](https://nginx.org/en/docs/control.html#reconfiguration)。

### Caddy：reload 命令 / /load 端点 + 可选文件监视

- `caddy reload` 等同于向 admin API 的 `/load` 端点 POST 新配置，是变更运行配置的正规方式；admin 端点关闭则该命令不可用。`caddy run --watch` 监视配置文件并自动重载，官方标注「仅限本地开发环境」。另有 `caddy validate` 先验配置。来源：[Caddy command line](https://caddyserver.com/docs/command-line#caddy-reload)、[Caddy API](https://caddyserver.com/docs/api)。

### Kong：DB-less 声明式配置 + /config 整体替换

- DB-less 模式下实体配置是声明式文件，`POST /config` 把内存里的整套实体替换成文件内容；`kong config parse` 先做语法检查；替换是「整份声明状态」而非逐条命令，避免中间态。来源：[Kong DB-less and Declarative Configuration](https://docs.konghq.com/gateway/latest/production/deployment-topologies/db-less-and-declarative-config/)。

### APISIX：etcd 动态 + stand-alone 轮询 + 插件热重载

- 默认 etcd 模式：路由/上游通过 Admin API 增删改，毫秒级生效、不重载不丢连接。来源：[APISIX vs NGINX 对比](https://apisix.apache.org/learning-center/tags/nginx/)。
- stand-alone 模式用 `apisix.yaml` 做配置中心，启动后周期性重读该文件更新配置。来源：[APISIX stand-alone](https://apisix.apache.org/docs/apisix/stand-alone/)。
- Lua 插件可用 `PUT /apisix/admin/plugins/reload` 热重载，不重启进程。来源：[APISIX Admin API](https://apisix.apache.org/docs/apisix/admin-api/)。

### Prometheus：SIGHUP / -/reload，坏配置不生效

- 运行中重载由 SIGHUP 触发，或开启 `--web.enable-lifecycle` 后 POST `/-/reload`；新配置不合格式则变更不应用。来源：[Prometheus Configuration](https://prometheus.io/docs/prometheus/latest/configuration/configuration/)。

### Kubernetes controller：reconcile 循环

- 控制器是控制循环：观察当前状态 → 与期望状态比较 → 执行动作拉近 → 重复；按水平触发（level-triggered）语义运行，漏了事件也会在下一轮补齐，最终一致。期望状态来自 spec，变更前可经校验 webhook 拦截。来源：[Kubernetes: Controllers](https://kubernetes.io/docs/concepts/architecture/controller/)。

### Go 生态 fsnotify：原子写与半写

- 编辑器普遍原子保存：先写临时文件再 rename 覆盖；只监视单个文件会在 rename 后丢 watch，官方建议监视父目录并按 `Event.Name` 过滤。来源：[fsnotify README](https://github.com/fsnotify/fsnotify#watching-a-file-doesnt-work-well)。
- K8s ConfigMap 通过 symlink 挂载，更新是换链接，要盯 Remove/重挂事件，不能只盯 Write。来源：[Go fsnotify and Kubernetes ConfigMaps](https://martensson.io/posts/fsnotify-k8s-configmaps/)。
- 共性坑：rename 瞬间、写入中途（半写）读文件都会拿到不完整内容——必须先整读、解析、校验，再切换。

## 什么适合 GQY

- **整体快照替换**（Kong / Nginx / Prometheus 共识）：GQY 单进程单文件，配置是「声明式整份状态」，一次重载换一整套快照，不做逐字段增量。
- **校验失败保留旧配置**（Nginx / Prometheus）：解析或校验不过，回滚到旧快照，不半新半旧。
- **新请求用新快照、在途请求用旧快照**（Nginx / Envoy / HAProxy）：GQY 不需要双进程，用不可变快照 + 每次请求开始时取一次快照即可达到同等语义。
- **手动重载端点**（Caddy / Kong / Prometheus）：`POST /api/config/reload`，给「改文件不方便」的场景兜底，也便于测试与状态确认。
- **目录级监视 + 事件合并**（fsnotify 官方建议 + k8s controller 水平触发）：监视 `$GQY_HOME` 配置目录而不是单个文件，事件去抖合并，半写与 rename 都能防住。
- **声明式整体校验再应用**（Kong `config parse`、APISIX schema validate）：重载管线里放结构校验（id 唯一、成员存在、上限），复用 `02-网关与路由.md` 的规则。

## 什么不采用

- **xDS / 控制面下发**（Envoy、APISIX etcd、Kong 控制面）：GQY 单机单用户，没有第二个进程做控制面；文件就是控制面。
- **双进程 / 热重启接管 socket**（Envoy hot restart、HAProxy `-sf`、Nginx worker 交接）：为「在途请求用旧配置」上双进程太重，GQY 用快照语义就够。
- **逐资源增量 CRUD**（APISIX Admin API、Kong 有库模式）：增量产生中间态；GQY 保持整份声明式。
- **etcd / 数据库做配置中心**（APISIX、Kong 传统模式）：违反 G1 本地优先，多一个外部依赖。
- **无限轮询重读文件**（APISIX stand-alone 周期轮询）：GQY 用 fsnotify 事件驱动，只在变化时重载；轮询浪费且响应慢。
- **配置文件自动监视作为生产默认**（Caddy `--watch` 标注仅本地开发）：GQY 本身是本地单机工具，自动监视是主路径，但保留关闭选项，供批量改文件时防抖。

## 采用 / 不采用

| 做法 | GQY 采用 | 说明 |
| --- | --- | --- |
| 声明式整份配置 + 整体快照替换 | 是 | providers.json / routing.json / settings.json |
| 解析 → 校验 → 原子切换，失败保留旧配置 | 是 | 校验规则复用 02 的决定 |
| 新请求新快照、在途请求旧快照 | 是 | 不可变快照，不用双进程 |
| 手动重载端点 POST /api/config/reload | 是 | 鉴权走 GQY_AUTH_TOKEN；可选 SIGHUP |
| 目录级 fsnotify 监视 + 事件合并 | 是 | 防半写、防 rename 丢 watch |
| 密钥只写不读，重载不泄漏 | 是 | 延续 R5 |
| 重载结果进状态接口与日志 | 是 | 版本号、最近一次重载时间/错误 |
| xDS / 控制面动态下发 | 否 | 单机不需要控制面 |
| 双进程热重启接管 socket | 否 | 快照语义已够，不引入双进程 |
| 逐资源增量 CRUD | 否 | 增量产生中间态 |
| etcd / 数据库配置中心 | 否 | 违反 G1 本地优先 |
| 周期轮询重读文件 | 否 | 事件驱动比轮询好 |
